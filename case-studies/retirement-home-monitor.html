Intelligent Retirement Home Monitor — Dual-Model Computer Vision & Resident Care Platform

A cross-platform resident care platform pairing two complementary TensorFlow computer vision models — one detecting falls as events, one detecting the absence of expected motion over time — alongside medication scheduling, appointment reminders, and multi-modal caregiver chat, deployed in Flutter over a Firebase backend.

Role
Full-stack contributor — team project
Platforms
Android primary · Web build · Windows partial
CV Stack
Python · OpenCV · TensorFlow — dual models
Backend
Firebase — Auth · Firestore · Cloud Messaging

Elderly residents in care facilities face a specific class of risk: the events that matter most are the ones where nothing obviously happens. A fall is visible and loud, but a resident who stops moving quietly — who becomes unresponsive in their chair, or who hasn't left their bed in eight hours — is the more dangerous case, because the absence of activity is precisely what makes it easy to overlook.

This project set out to build a resident care platform that monitored both failure modes simultaneously, alongside the routine administrative tools a facility actually operates on: medication schedules, doctor appointments, and a communication channel between residents, caregivers, and family. It was a group project — our team of developers built the system collaboratively across a single semester — and the deliverable was a functional cross-platform application with Android as the primary release target.

PHASE 01

System Architecture & Technical Stack

The platform was built as three cooperating layers: a Python-side machine learning service running the computer vision models, a Flutter client providing the user interface across Android, web, and Windows, and a Firebase backend connecting the two and handling authentication, data persistence, and push notifications.

The three-layer architecture

  • Computer vision layer — Python, OpenCV, TensorFlow. Two independently trained TensorFlow models process video frames captured through OpenCV and classify the resident's current state. This layer is where the actual intelligence of the system lives — everything else exists to deliver its outputs to the right person.
  • Application layer — Flutter. A single Dart codebase compiled for Android, web, and Windows. The Flutter client handles all user-facing functionality: resident profiles, medication scheduling, appointment tracking, chat, and the alert notifications triggered by the CV models.
  • Backend layer — Firebase. Firebase Authentication for user identity and role management, Cloud Firestore for resident records and event logs, and Firebase Cloud Messaging for push notifications to caregiver devices. This layer is what makes the CV detections useful — a model that identifies a fall is only valuable if the alert actually reaches the attending nurse in seconds.

The three-layer split was deliberate and had real consequences for the project's development velocity. Because the CV layer communicated with the app layer through Firebase rather than through direct API calls, each side of the team could develop against a well-defined interface without waiting for the other to be finished. The modelling work could proceed against a mock data pipeline while the Flutter UI was still being designed, and vice versa.

PHASE 02

Dual Computer Vision Models

The technical core of the platform was a pair of TensorFlow models, each trained to detect a different kind of danger. The design insight that shaped the whole project was recognising that these two failure modes are structurally different problems — one is about detecting an event that happens, the other about detecting the absence of events that should be happening — and that trying to solve both with a single model would have been a mistake.

Model 1 — Fall detection

The first model addresses the acute case: a resident trips, loses balance, or collapses. This is an event-detection problem. The model observes a video stream, recognises the visual signature of a fall — a rapid vertical drop in body position combined with a change in body orientation from vertical to horizontal — and fires an alert to the caregiver network the moment the pattern is confirmed.

The technical challenge here is not detecting a fall in a controlled scenario; it's detecting falls reliably in a real environment. A person sitting down quickly looks a lot like a person falling until the final frame, and a resident bending over to pick something up produces a similar vertical shift without any actual fall occurring. Preventing false positives was the dominant constraint on the model's design — an alert system that cries wolf gets ignored by caregivers within a week, at which point it stops being a safety feature and starts being a liability.

The alert delivery path was straightforward once detection succeeded: the confirmed fall event was written to Firestore, which triggered a Cloud Messaging notification to every caregiver device registered to that resident. The attending nurse, the on-duty doctor, and any family members with the app received the alert simultaneously, along with the timestamp and resident identifier — a push-based notification model that delivers in seconds rather than requiring anyone to be actively watching a dashboard.

Model 2 — Inactivity detection

The second model addresses the quieter and more insidious case: a resident who simply stops moving. This is an absence-detection problem — and it's structurally harder than fall detection, because there's no moment of visible change to key off. The model has to know what "normal inactivity" looks like for a given resident, and then recognise when the observed inactivity has crossed from rest into something medically concerning.

The design pattern we settled on was a temporal window analysis: the model tracks the resident's motion over a rolling time window, and if the amount of detected movement falls below a threshold for longer than that window allows, it fires an alert. The threshold and window length had to be configurable per resident, because a healthy elderly person and a resident recovering from surgery have very different normal-motion profiles. Getting this calibration right was as important as the model itself — a single fixed threshold would either miss real emergencies or trigger on perfectly normal sleep.

The alert path for inactivity used the same Firebase pipeline as the fall model, but with different urgency framing. Fall alerts fire immediately and demand an urgent response. Inactivity alerts fire after a defined delay and prompt a wellness check rather than an emergency response — the caregiver is asked to confirm the resident is responsive before escalating. This distinction matters operationally; treating a long nap the same as a fall would make the platform unusable in practice.

Why two models rather than one

Combining both detections into a single model was considered and rejected early. The two problems have different input structures (one looks at a short time slice around an event, the other at a long time window), different output types (event classification versus threshold-based anomaly detection), and different false-positive costs. Trying to unify them would have produced a model that was mediocre at both tasks instead of good at each. Keeping them separate meant each could be trained, tuned, and evaluated against its own success criteria without compromising the other.

PHASE 03

Companion Care Features

Beyond the computer vision layer, the platform provided the routine administrative and communication tools that a care facility actually runs on day to day. These features weren't AI-powered — they were the practical capabilities that made the app worth opening even when nothing was going wrong.

Medication scheduling

Residents in care facilities typically take multiple medications on different schedules — some daily, some twice daily, some as-needed — and missed doses are one of the most common and consequential failure modes in elderly care. The platform provided a medication scheduler where each resident's prescriptions were entered once with their dosages and schedules, and the system generated both reminder notifications to the resident and confirmation prompts to the assigned caregiver. The caregiver confirmation step was deliberate — it turned the schedule from an informative list into an auditable record of whether the medication was actually administered.

Doctor appointment reminders

The same notification infrastructure was reused for appointment tracking. Upcoming doctor visits were recorded with date, time, location, and provider, and the system pushed reminders to both the resident and their caregiver in the days leading up to the appointment. The dual-recipient model mirrored the medication feature — the resident gets the reminder so they're aware, and the caregiver gets it so they can arrange transport and accompaniment if needed.

Multi-modal caregiver chat

The final feature was direct communication between residents, caregivers, and family members through the app itself. Three communication modes were supported:

  • Text chat. Standard asynchronous messaging — the baseline channel for quick coordination between caregivers, or between a resident and their family.
  • Audio messaging. Recorded voice messages that could be sent when typing wasn't convenient, or when a resident preferred speaking to writing. This mattered more than expected — many elderly users find voice interfaces significantly more accessible than on-screen keyboards.
  • Audio + video calling. Live two-way communication for cases where real-time interaction was needed — a family member checking in on their parent, or a caregiver consulting with an on-call doctor.

The chat infrastructure was built on Firebase's real-time capabilities, which handled the message persistence and delivery layers without requiring us to build or host a custom messaging backend. This was the right engineering trade-off for a project of this scope: rebuilding real-time messaging from scratch would have consumed time that was better spent on the computer vision work that made the platform distinctive.

PHASE 04

Cross-Platform Deployment & Platform Prioritisation

Flutter's promise is a single codebase that compiles to every major platform. In practice, the platform-specific reality of the underlying backend SDKs complicates that promise considerably — and this project ran directly into that constraint.

The Firebase plugin gap on Windows

Firebase ships official SDKs for Android, iOS, and web. Its Windows support — while present for some services — was incomplete at the time we were building, meaning that several of the platform's core capabilities couldn't be relied on in the Windows build. Firebase Cloud Messaging for push notifications, in particular, was not fully supported on the Windows Flutter target, which meant the alert-delivery mechanism at the heart of the CV layer couldn't work on that platform.

The team faced a decision that's common in cross-platform development but rarely discussed honestly: which platforms do we actually support, given that the underlying technology doesn't support them all uniformly?

The prioritisation decision

The resolution was a deliberate three-tier platform strategy:

  • Tier 1 — Android (primary release target). Full feature parity across every capability: CV alerts, medication and appointment notifications, chat with all three communication modes. Android was chosen as the primary target because it's the platform most caregivers actually carry — it's what a nurse has in their pocket during a shift.
  • Tier 2 — Web (secondary, functional). The web build worked for the administrative and communication features but couldn't reliably receive the push notifications that the CV layer depended on. It was useful as a management interface — viewing resident records, editing medication schedules, reviewing historical event logs — but not as a real-time alert channel.
  • Tier 3 — Windows (partial, deprioritised). The Windows build compiled and ran, but several Firebase-backed features were either unavailable or unreliable due to incomplete plugin support. Rather than shipping a Windows version that silently failed to deliver the alerts the platform was built to provide, we documented it as a partial build and focused engineering effort where it would actually be used.

This tier structure wasn't a compromise — it was the correct engineering answer to a real constraint. Trying to force the Windows build to full parity would have meant either rebuilding the notification pipeline on a non-Firebase backend for that platform alone, or waiting for the Firebase plugin ecosystem to catch up. Neither was a good use of the project's remaining time. Prioritising Android to production quality and shipping a functional web admin interface was a decision that actually delivered value, rather than a decision that pretended every platform was equally viable.

◆ LESSON_IN_PLATFORM_PRAGMATISM

"Cross-platform" doesn't mean "identical everywhere." The honest engineering position is that Flutter gives you one codebase, but the platform-native capabilities underneath it — push notification delivery, background processing, permission models — still vary. Recognizing where those gaps are and prioritising accordingly is what turns a cross-platform claim into a cross-platform delivery. This lesson transferred directly to later work: every platform claim in a project plan should be qualified by what the underlying stack actually supports on that platform.

OUTCOMES

Project Outcomes

The delivered system combined a working computer vision layer with a fully-featured Flutter application and a production-grade Firebase backend, deployed across Android as the primary release target with web and Windows support documented by capability tier.

  • Dual-model computer vision pipeline. Two independently trained TensorFlow models — one for event-based fall detection, one for absence-based inactivity detection — each tuned to its own failure mode and calibrated against the specific false-positive costs that would have made either model unusable in practice.
  • Complete resident care application. Medication scheduling with dual notification to resident and caregiver, appointment tracking with reminders, and multi-modal chat supporting text, audio, and audio-video — a full feature set, not a proof-of-concept.
  • Cross-platform delivery with honest scoping. A single Flutter codebase deployed to three platforms, with the primary Android release receiving full feature parity and the web and Windows builds documented by what they actually supported. The tier structure reflected the real constraint imposed by incomplete Firebase plugin support on Windows, rather than an aspirational claim about cross-platform parity.
  • Firebase-backed alert delivery proven in principle. The pipeline from CV detection to caregiver notification was architected end-to-end — model output written to Firestore, Cloud Messaging triggered by the write, notification delivered to every registered caregiver device within seconds — with the significant caveat that this pipeline only functioned on platforms where the notification SDK was available.
✓ SYSTEM_ARCHITECTURE_VALIDATED

Full-stack resident care platform delivered as a team project. The engagement demonstrated the ability to coordinate a multi-layer system — a Python machine learning service, a Flutter cross-platform client, and a Firebase backend — across a collaborative team, with each layer developed against a well-defined interface and the whole system delivered to a functional release state. The two technical lessons that carried forward most strongly were the structural distinction between event-detection and absence-detection computer vision problems, and the importance of scoping cross-platform claims against what the underlying stack actually supports on each platform.
