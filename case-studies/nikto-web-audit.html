Web Application Vulnerability Assessment & Server Hardening Audits

A comprehensive application-layer assessment with Nikto against a live Apache2 instance on Ubuntu Server 24.04 LTS — exposing an ETag inode information-leak vector (CVE-2003-1418) and a systemic absence of modern HTTP security headers, then closing both with hardened configuration directives.

Environment
Kali Linux 2026.x → Ubuntu Server 24.04 LTS
Network Loop
192.168.40.0/24 — isolated virtual LAN
Target Service
Apache2 HTTP daemon · port 80/tcp
Scanner
Nikto Web Scanner · 8,113 request queries

To perform a realistic application-layer vulnerability assessment, an active corporate web portal hosting environment had to be simulated across the virtual network. This engagement demonstrates server-side deployment configuration, hot-patching host firewalls to permit authorised test traffic, capturing application header vulnerabilities, and mapping the resulting compliance gaps against standard security baseline metrics.

◆ SCOPE_CONSTRAINT

The web server was provisioned specifically for this audit inside an isolated 192.168.40.0/24 lab loop. Port 80 was opened to the firewall only for the duration of testing and closed again afterwards. No production data was ever in scope.

PHASE 01

Web Server Provisioning & Core Boundary Adjustments

The target environment was brought online with an enterprise-grade HTTP daemon installed directly from the Ubuntu repositories. Apache2 was selected because its default configuration mirrors the out-of-the-box deployment posture found in countless real-world organisations — which makes it a useful control sample for baseline auditing:

bash 
sudo apt install apache2 -y

With the service running but unreachable behind the default-deny firewall policy, a targeted hot-patch was applied to the UFW ruleset — creating a single authorised communication slot for unencrypted inbound web traffic on the standard HTTP port:

bash 
sudo ufw allow 80/tcp

That single rule is the entire attack surface under test. Everything from here forward runs through that one authorised slot — the perimeter is clean, the auditor's visibility is limited, and any finding must come from the application itself.

PHASE 02

Active Web Crawling & Vulnerability Interrogation

With the target listening on port 80, the Nikto Web Scanner was deployed from the attacking Kali platform to run deep directory crawls against the exposed service:

bash 
nikto -h 192.168.40.131

The scanner performed a systematic verification pass running over 8,113 discrete request queries — parsing exposed server traits, probing for dangerous default configuration scripts, and inspecting every application response header for compliance with modern security baselines.

FINDINGS

Forensic Assessment Results

The scanning matrix bypassed system boundaries successfully and exposed a clear list of configuration vulnerabilities directly within the server response profiles. Two categories of issue emerged from the telemetry.

Finding 01 — Information leakage via ETags

The server is emitting ETag response headers that encode file system inode numbers alongside the standard modification timestamp. This is a well-documented behaviour of the default Apache ETag configuration and it carries a public CVE designation:

INFORMATION_LEAK CVE-2003-1418

Server may leak inodes via ETags

External actors can observe the inode component of ETag headers and use it to reverse-engineer characteristics of the server's file system — including directory structure, file age distribution, and potentially the deployment layout. While each leak is small in isolation, aggregated across a live crawl it becomes actionable reconnaissance for a follow-up exploitation attempt.

Finding 02 — Missing defensive security headers

More significantly, the audit identified a systemic absence of modern HTTP security wrappers — the response headers that instruct client browsers how to defend themselves against advanced web exploits. Four headers were found missing from every response:

  • X-Content-Type-Options — missing. Without this directive, client browsers are exposed to MIME-sniffing attacks, where a malicious response can be reinterpreted as an executable content type and trigger cross-site scripting (XSS) drive-by payload executions.
  • Content-Security-Policy — missing. Absent a CSP policy, application data channels remain vulnerable to malicious script injections. The browser has no instruction set defining which origins may serve executable content.
  • Referrer-Policy — missing. Session-bearing URLs can leak to third-party destinations during cross-domain navigation, exposing internal paths and potentially sensitive query parameters in outbound HTTP referrer headers.
  • Strict-Transport-Security — missing. Fails to enforce strict encrypted communication requirements. Browsers have no persistent instruction to refuse plaintext requests to this origin, leaving the door open to downgrade and man-in-the-middle vectors once a TLS endpoint is added.
REMEDIATION

Closing the Findings

To secure this environment, the central Apache configuration file (/etc/apache2/conf-available/security.conf) must be modified to inject explicit Header set parameters that enforce all four missing secure HTTP responses — and to strip the inode component from ETag generation. Both fixes are applied in the same file before production deployment:

/etc/apache2/conf-available/security.conf 
# Disable inode leakage in ETag headers (CVE-2003-1418)
FileETag MTime Size

# Enforce modern client-side security wrappers
Header set X-Content-Type-Options "nosniff"
Header set Content-Security-Policy "default-src 'self'"
Header set Referrer-Policy "strict-origin-when-cross-origin"
Header set Strict-Transport-Security "max-age=31536000; includeSubDomains"
✓ HARDENING_STEPS

Enable the module that makes these directives active with a2enmod headers, then reload the daemon with systemctl reload apache2. The final validation step is to re-run nikto -h 192.168.40.131 and confirm that neither the ETag finding nor the missing-header warnings appear in the new crawl — a finding is only closed when the scanner confirms it.

OUTCOMES

Engagement Summary

  • Attack surface mapped with full application-layer visibility. 8,113 discrete queries produced a complete header and configuration profile of the target, isolating exactly two classes of issue from an otherwise default-clean deployment.
  • Compliance gaps quantified against baseline metrics. The missing security header suite represents a measurable deviation from current OWASP and PCI-DSS guidance — not a theoretical concern, but an audit-failing condition in regulated environments.
  • Remediation path defined and verifiable. Both findings resolve to concrete configuration changes in a single Apache file, with a re-scan step that deterministically proves closure.
