Enterprise Linux CLI Administration & Identity Hardening

Deploying Role-Based Access Control on a headless Ubuntu Server — user and POSIX group provisioning, a chmod 770 directory lockdown with chown root:accounting ownership hardening, and a live security audit proving that the authorization boundary holds under three distinct attack surfaces.

Environment
Ubuntu Server 24.04 LTS — headless (CLI-only)
Identity Model
POSIX users + POSIX group (accounting)
Permission Mask
drwxrwx--- (octal 770)
Ownership
root:accounting

File system permissions are the oldest and most reliable access control mechanism in the Unix model, and they are still the foundation of every enterprise Linux deployment. A firewall controls what traffic reaches a service; a permission mask controls what users can do with the data once they're on the machine. The two operate at different layers, and both are required for a meaningful security posture.

This engagement hardens a sensitive corporate directory using the standard Unix access control toolkit — users, groups, ownership, and permission bits — then validates the resulting security boundary against three distinct threat models: a legitimate user within the authorized group, an unauthorized user attempting access, and a privilege escalation attempt that tries to bypass the file permission model entirely. The goal is not merely to configure permissions but to prove they hold under load.

◆ SCOPE_CONSTRAINT

All work was performed in an isolated Ubuntu Server VM. The account names, group identifier, and file names used here reflect lab-only identities — they are not associated with any production directory, and the sensitive file created during the audit contains only placeholder data for testing purposes.

PHASE 01

Identity Infrastructure Provisioning

Role-Based Access Control begins with identity. Before a permission boundary can mean anything, the accounts and groups that will exist on either side of that boundary have to be defined — and each one needs a purpose. In this lab, three identities were provisioned with distinct roles:

  • oudaidev — the primary administrative account, the only user with full sudo privileges. This is the account that created the protected directory and installed the test file.
  • oliver_accountant — a standard user account provisioned specifically to be a member of the accounting group. This account represents an authorized business user whose job requires access to the financial directory.
  • claire_employee — a standard user account deliberately left outside the accounting group. This account represents any other employee in the organization — someone with a legitimate user account on the system, but no business justification for touching financial data.

The accounting group was created with a specific GID, and oliver_accountant was added to it as a supplementary group membership. Crucially, claire_employee was not added — and that single decision is what the entire permission model will enforce. The group membership is the authorization boundary.

bash 
# Provision the accounting group and its two standard users
sudo groupadd accounting
sudo useradd -m -s /bin/bash oliver_accountant
sudo useradd -m -s /bin/bash claire_employee

# Add only the authorized user to the accounting group
sudo usermod -aG accounting oliver_accountant

# Confirm group membership
getent group accounting

The getent group accounting output confirms the membership list — the accounting group exists with the correct GID, and oliver_accountant appears as its only member. claire_employee is conspicuously absent. That absence is the whole point of the exercise; everything from here forward is about proving the operating system respects it.

PHASE 02

Directory Lockdown — chmod 770 & chown Hardening

With the identities in place, the protected resource was created. A directory named /company_financials was established at the root of the file system — a deliberate choice, because placing sensitive data at the top level makes it visible to any future administrator inheriting the system, which is exactly what you want for a corporate directory that a business function depends on.

Two distinct operations were then applied. The first was the ownership hardening via chown: the directory's owning user was set to root and its owning group was set to accounting. This is a critically important decision that is easy to miss. If the directory were owned by oliver_accountant instead, then any user who compromised oliver's credentials would inherit full control — the entire authorization model would reduce to "whoever has oliver's password wins." By making root the owner, the directory is anchored to the system administrator identity, and the accounting group is the only non-root identity that can touch it.

The second operation was the permission mask via chmod 770. The three-digit octal notation encodes three separate permission sets — one for the owner, one for the group, and one for everyone else:

  • Owner permissions (root) — 7 = rwx. Full read, write, and execute access. The owner is the administrator and can do anything to the directory.
  • Group permissions (accounting) — 7 = rwx. Full read, write, and execute access. Members of the accounting group can list, read, create, modify, and delete contents inside the directory — exactly the access the accounting team requires.
  • Others permissions — 0 = ---. No permissions whatsoever. Users who are neither the owner nor members of the accounting group cannot even list the directory contents, let alone read or write anything inside it.
bash 
# Create the protected directory and its dummy test file
sudo mkdir /company_financials
echo "CONFIDENTIAL REPORT: Q3 Store Revenue Data" | sudo tee /company_financials/revenue_report.txt

# Harden ownership: root owns it, accounting group controls it
sudo chown root:accounting /company_financials

# Apply the 770 permission mask
sudo chmod 770 /company_financials

# Confirm the resulting state
ls -ld /company_financials

The resulting ls -ld output reads drwxrwx--- 2 root accounting. Every character in that string is doing work:

  • d — the entry is a directory, not a file.
  • rwx — the owning user (root) has full access.
  • rwx — members of the owning group (accounting) have full access.
  • --- — everyone else has no access at all.
  • root accounting — ownership is anchored to the system administrator identity, with the accounting group as the sole authorized non-root entity.

This is the classic expression of the Principle of Least Privilege: each identity has exactly the access it needs and no more. The accounting team gets full control of their data; the rest of the organization gets nothing; and no individual user account is empowered to unilaterally change the boundary.

PHASE 03

Security Audit — Three Attack Surfaces Tested

A permission configuration is only as good as its enforcement. Three distinct tests were run to validate that the boundary held under different threat models, each one representing a class of user behavior the directory needs to correctly handle.

Test 01 — Authorized access

The first test was the positive case: an authorized member of the accounting group attempting to access the directory. The accounting user session was invoked via su - oliver_accountant, and the directory was listed with ls /company_financials. The command executed without error and returned the directory contents — the authorization boundary correctly recognized oliver as a member of the owning group and granted the access his role requires.

Test 02 — Unauthorized access blocked

The second test was the negative case: a standard user without accounting group membership attempting the same operation. The session was switched to claire_employee, and the same ls /company_financials command was issued. The result was immediate and unambiguous:

bash 
claire_employee@ubs2604vm:~$ ls /company_financials
ls: cannot open directory '/company_financials': Permission denied

The Permission denied message is produced by the Linux kernel itself, not by the shell — the ls command attempted to open the directory and the kernel's Virtual File System layer intercepted the system call before any file descriptors were allocated. This is the crucial architectural detail that makes Unix permissions different from application-level access control: the enforcement is at the kernel level, and no userspace program — however it is written or what libraries it links against — can bypass it. Claire cannot read the directory contents, cannot list filenames, and cannot even confirm the directory exists as anything more than an opaque entry.

Test 03 — Privilege escalation blocked

The third test was the most important from a security standpoint, because it addresses the natural workaround any unauthorized user will reach for first: trying to use sudo to gain temporary administrative privileges and bypass the permission model. From the oliver_accountant session, an attempt was made to write directly into the protected directory via sudo tee. The result was a hard authentication rejection:

bash 
oliver_accountant@ubs2604vm:~$ echo "CONFIDENTIAL REPORT: Q3 Store Revenue Data" | sudo tee /company_financials/revenue_report.txt
[sudo] password for oliver_accountant:
sudo: I'm sorry oliver_accountant. I'm afraid I can't do that

The sudo denial message — borrowed from a well-known science fiction film, as it happens — is emitted by sudo's authentication layer when the requesting user is not present in the sudoers configuration. This confirms the second security layer enforced in the environment: not only is oliver_accountant not authorized to override the permission model, but no standard user account is. Only the primary administrative account (oudaidev) has sudo privileges, and that is a deliberate separation of duties. The accounting team has full access to their data through the group mechanism; the system administrator has full access to everything through the sudo mechanism; and neither can be used to short-circuit the other.

OUTCOMES

Verification Results

The audit produced three verifiable outcomes, each mapping to a distinct security property that the configuration was designed to enforce.

  • Authorization boundary operates as specified. Authorized group members gain access without friction; unauthorized users are denied at the kernel level; there is no configuration where the boundary is respected sometimes and ignored other times. The permission model is not a suggestion — it is enforced by the same subsystem that mediates every file system operation on the machine.
  • Privilege separation is enforced at two independent layers. The group membership model controls who can access the directory, and the sudo configuration controls who can elevate to administrator privileges. Both layers are required for meaningful security: without the first, any account could read the directory; without the second, any account could simply grant itself the access it wants. The combination produces defense in depth against both accidental misuse and deliberate bypass attempts.
  • Principle of Least Privilege demonstrated end-to-end. Every identity in the environment has exactly the access their role requires and nothing more. oudaidev administers the system but has no business accessing financial data through the group mechanism (and vice versa); oliver_accountant accesses the financial directory but cannot elevate to administrator; and claire_employee has a normal user session but touches none of the sensitive resources. This is the access pattern that every enterprise RBAC deployment aspires to, demonstrated at the file-system level with verifiable telemetry.
✓ RBAC_VALIDATED

Role-Based Access Control confirmed operational. The hardened directory provides full access to its authorized group, denies access to unauthorized users, and resists escalation attempts through the sudo path — all three properties verified through live terminal sessions rather than asserted through documentation. The configuration is a working example of the principle that a security control is only real when it has been tested against the threats it exists to stop.
