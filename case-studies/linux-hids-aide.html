Enterprise Linux HIDS Hardening & File Integrity Monitoring

Deploying the Advanced Intrusion Detection Environment (AIDE) as a host-based intrusion detection system — building a cryptographic SHA-256/SHA-512 baseline across 111,249 files, then proving detection fidelity by simulating an insider tampering event and catching it with byte-level forensic precision.

Environment
Headless Ubuntu Server 24.04 LTS (CLI-only)
Hypervisor
Type-2 VMware virtual machine
Engine
AIDE (Advanced Intrusion Detection Environment)
Hash Suite
SHA-256 · SHA-512 · file metadata

Advanced persistent threats often install silent backdoors inside core system configuration folders — appending malicious access lines to authentication files, for example, or replacing a single line inside a service configuration. Because the file profile can appear completely unaltered to standard system utilities, signature-based antivirus fails to catch the breach. The only reliable defence is cryptographic comparison against a known-good state — and that is exactly what a host-based intrusion detection system provides.

◆ SCOPE_CONSTRAINT

This engagement is conducted entirely inside a lab VM. The "breach" simulated in Phase 2 is a deliberate self-inflicted modification performed by the analyst — not a live compromise. The purpose is to validate detection metrics, not to investigate an incident.

PHASE 01

HIDS Infrastructure Calibration & Baselining

The AIDE engine was installed directly from the Ubuntu repositories. Its job is to fingerprint every protected file on the system — computing cryptographic hashes, recording ownership and permission metadata, and storing the whole inventory in a tamper-evident database that becomes the server's known-good identity:

bash 
sudo apt install aide -y

With the engine in place, an absolute system baseline was generated. The automated scanning module crawled the entire server framework, calculating high-precision SHA-256 and SHA-512 hashes for every protected configuration asset and cataloguing the server's healthy baseline identity:

bash 
sudo aideinit

The final step in Phase 1 is to arm the guard — promoting the freshly generated database from its initial .new state into the location AIDE reads during verification. Until that promotion happens, the engine has a baseline but no active reference to compare against:

bash 
sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db
✓ BASELINE_ARMED

The system is now in a clean operational checkpoint state. Every file AIDE protects has been reduced to a cryptographic fingerprint, and any future modification — even a single bit — will produce a hash mismatch that the engine can surface on demand.

PHASE 02

Mock Breach Simulation & Anomaly Auditing

To evaluate the detection metrics of the armed HIDS engine, a local system breach was simulated. Acting as a malicious insider, an unauthorised string injection payload was forced into the server's primary network hostname translation dictionary — the classic "append a backdoor to /etc/hosts" move that would redirect a legitimate domain to an attacker-controlled IP in a real intrusion:

bash 
echo "malicious_backdoor_payload_active=true" | sudo tee -a /etc/hosts

From the operating system's perspective, nothing has changed. The file still exists, still has valid permissions, still serves DNS resolution correctly. There is no signature, no running process, no anomalous network traffic. This is precisely the class of intrusion that conventional defences miss.

With the tampering in place, an administrative threat-hunting verification scan was manually triggered to compare the active runtime state of the operating system against the trusted cryptographic baseline:

bash 
sudo aide --check --config /etc/aide/aide.conf
OUTCOMES

Forensic Verification Results

The HIDS engine bypassed configuration environment path conflicts and audited 111,249 file system entries, generating a comprehensive Host Integrity Report that detailed every post-baseline variation across the entire server layout.

The executive alert

The kernel tracking engine flagged anomalous activity across the system layout and raised the alert that matters:

INTEGRITY_DRIFT aide --check · 21 changes

21 changed entries detected across 111,249 audited files

From over a hundred thousand protected file paths, the engine isolated exactly 21 entries whose cryptographic fingerprints no longer matched the baseline. This is the detection signature of a successful FIM deployment — not a flood of noise, not a miss, but a precise, bounded alert an analyst can act on immediately.

The forensic fingerprint

The detailed log module isolated the exact compromised target directory and exposed the attacker's full footprint:

  • Target file. /etc/hosts — flagged as the modified asset, confirmed by direct comparison against the baseline entry.
  • File size delta. Growth from 224 bytes to 263 bytes — an increase of exactly 39 bytes, which matches the character count of the injected payload string plus the trailing newline appended by tee. The file size delta alone tells you the payload length.
  • Timestamp drift. A modified mtime recorded on the file, cross-referenced against the baseline creation timestamp to establish the exact window during which the modification occurred.
  • Cryptographic mismatch. Completely altered SHA-256 and SHA-512 hash profiles — the definitive evidence that the file content changed, independent of any metadata observation.
✓ DETECTION_VALIDATED

100% detection visibility confirmed. If an unauthorised process alters even a single bit of structured code on the endpoint, the baseline drift is exposed instantly. The 21-entry alert was not a coincidence — the engine knew exactly which files diverged from the trusted state, down to the byte.
